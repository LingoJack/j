5 Function Calling
工具的原理是 function calling
先说 LLM 的输入结构。
每次请求，LLM 收到的就是一组 messages 和 system prompt
System prompt 是全局指令，会把身份设定、行为规则、工具的 Schema 都写在里面
messages 有 User ， assistant 和 system 三个角色。分别是是用户消息，ai 回复消息和思考、系统提示词
这个消息数组就是 LLM 能看到的所有东西。上下文指这些。后面整章上下文治理基本上都是围绕这件事展开的。
Function Calling 就是在这个基础上约定。把工具 Schema 写进 System prompt，LLM 推理后只输出一段 tool_calls JSON
本地程序 拿着 JSON 真正去执行，再把结果作为消息写回。

13 上下文治理 · 问题与路径
ReAct 的本质决定了窗口必然会被工具结果不断挤占；上下文到达高水位，模型出幻觉、服务不可用的概率大大提高。
我们做了三个方向来治理上下文：分级压缩、优先级窗口、动态状态感知。

14 分级压缩 + 豁免
压缩分两级：
micro 把较早轮次的工具调用换成占位符，程序化操作，快且可控，每小轮 Agent Loop 触发；
auto 调 LLM 把整段历史摘要后清空再写回，彻底但贵且不可控，只在高水位触发。
这里有一个设计是豁免机制：
用户消息、Plan、TodoWrite、SubAgent 结论这些方向性消息不参与压缩，只压缩 Read、Bash、Edit 这种衰减极快的执行结果。

15 优先级窗口
传统的滑动窗口固定取最近 N 条消息，这么做导致方向性消息容易被后来的执行消息挤出窗口。
所以给不同消息打上不同的价值再按 3:6:1 的比例填窗——30% 给方向性消息、60% 给近期上下文、10% 给执行细节。
和背包问题不同的是不能完全没有低价值的执行消息，否则 AI 容易凭空猜测不调用工具

16 动态状态感知
Agent 还需要知道"窗口外正在发生什么"。这里做了 System Prompt 和 messages 两层注入。
前者占位符每轮替换为后台任务、队友状态等实时快照；
后者则处理通知提醒事件，用特殊的xml标签包裹消息写入，不打断，Agent 在下一次构建messages数组时自然看到。

17 长程实测
上述措施配合指数退避随机等待来处理API 故障和限频，可稳定跑到 2000 多轮消息窗口始终维持在健康水平、方向不跑偏。
这里只是取了运行比较长久的一个记录。实际上限会更高

19 工具体系 · 渐进增强
有 Read、Write、Bash、LoadSkill 这几个工具 Agent 便能工作
工具不是越多越好。本次实现面向频繁场景，适当增加增强一些工具。下面选三个典型展开。

20 Plan + 审批清空
第一是引入 plan 工具进入只读状态和 approval and clear context 机制清理调研中间产物、保留最终计划文件强化 agent 的方向规划能力并节约上下文

21 清空后执行
Agent 忘掉调研细节，执行阶段窗口干净，复杂bug修复成功率明显提高，且搭配豁免机制，方向性强。

22 Edit · 精确替换 + 凭证握手
Edit 工具做了两样增强。
一是优化工具反馈。唯一匹配失败会给出诊断、匹配多次会提示加上下文以达到唯一匹配。
二是增加批量选项。批量选项开启时不直接执行，先返回预览和文件摘要凭证
AI 预览变更，把凭证回传才执行替换；
利用文件改变后摘要凭证改变就失效的原理，避免模型思考中途文件被外部更改不感知导致的错误。

23-24 Bash 执行三态（合并讲）
Bash 状态流转是从一个死锁案例倒推出来的。
当时 Agent 跑一个常见 vite 模板的命令。这个命令是交互式的。
进程在等用户按回车、Agent 在等 命令的输出，陷入死锁。
所以给 Bash 命令引入了状态流转规则：命令执行超过预设时间，升级为后台运行返回 task_id，并且做做静默检测。
如果一直没有任何输出，那么判断在等待交互输入，给 Agent 提示加 -y；
后续 Agent 凭借 task_id 可以调用 TaskOutput 工具等待结果，或 Session 工具操作标准输入输出处理交互

26 多 Agent · 两种模式
多 Agent 以 subagent 和 teammate 两个工具体现。
Teammate 是协作者，有独立窗口和工具集，通过共享聊天室沟通。
SubAgent 是临时的，有独立窗口，执行完只把一段精简摘要回灌给主 Agent。主 agent 可以以很小的代价了解陌生模块。

28-29 实验一 · 轮流报数（合并讲）
第一个实验是两个协作者交替报数来验证消息传递与触发唤醒机制。
实验发现了过期快照导致重复消息的问题。思考时间很长，导致期间新的消息和思考快照消息存在偏差，引起对外的不一致，这里说对外是对用户、对其他 Teammate
于是给 SendMessage 工具加一个二阶段提交门禁：
发消息工具先检查信箱有没有新消息，有就 hold 住、注入提醒、让 Agent 看到最新状态后再决策。
修复后 10 个数字全部正确报出、无人工干预

30 实验二 · 续写接龙
实验二是多个协作者轮流续写故事，通过人物时间线是否一致，逻辑是否自洽检验协作者基于共同事实工作的能力。
结果是 13 轮全部完成、偏题 0 次；只有 1 次内容重复，但符合逻辑预期

31 实验三 · 开发-测试协作
实验三是工程场景。
Anthropic 的文章指出模型对自己的工作有偏袒，让另一个 Agent 来评审才能拿到更客观反馈。

34 模板代码 · 问题
业务系统里有大量数据结构相关的高度模板化的代码。
经过实验，LLM 逐字生成 51 张表的 DAO，结果漏了 11 个字段、4 个索引方法，烧了 24M token、跑了 53 分钟、压缩触发了 67 次。
这是长链路推理的系统性风险。

35 核心观察
但仔细看这类代码会发现，它几乎不需要创造性决策：字段名、类型、索引直接决定有查询方法，数据实体长什么样。
DDL 已经是数据层代码的充分输入。
这部分不让 LLM 来推理，交给确定性生成器更合适

36 jen 架构
jen 的原理四步：输入 schema、解析索引语义、用 Go template 渲染、输出按主键/唯一索引/普通索引派生的原子方法集。
稳定，确定，没有字段漂移。

37 jen 实测对比
同一份 schema 做对照，jen 把 token 降到了 1/50、耗时降到 1/27、字段一致性 100%。
把规则稳定、容易漂移的部分剥离出来，模型专注在业务逻辑和契约定义上。

38 webapp-gen 全栈工作流
把 jen 嵌进一个更大的流程，就是 webapp-gen。
webapp gen 是一条 11 步流水线：
模板脚手架前置 → 文档驱动定契约 → mock 原型反馈闭环 → jen 生成数据层 → 后端编码 → 容器化验收。
主要考虑是接口和契约优先、从原型出发逐步替换完善系统
