## 第 4 页 · ChatBot vs Agent

这个项目的出发点很直接——过去用 ChatBot 辅助写代码的时候，是复制代码、报错、配置贴给模型，再按给出的建议手动修改；而 Agent 让这件事由程序通过协议自己进行，把人从这个过程的多数时间抽离出来

---

## 第 5 页 · Function Calling

那程序是怎么做到这件事的呢？是 ReAct 范式加 Function Calling 协议这一套。
先说 LLM 的输入结构。
每次请求，LLM 收到的就是一组 messages，分三种角色：
System 是全局指令，会把身份设定、行为规则、工具的 Schema 都写在里面
User 是用户输入，也包括运行时注入的提醒
Assistant 是 LLM 自己的回复。
这个 messages 数组就是 LLM 能看到的全部世界——它没有记忆、没有硬盘，所有东西都在这个数组里。

数组里的消息有价值高低：用户的需求和 Agent 的决策属于方向性的，价值高；中间那些工具读出来的文件内容、命令输出，看一眼就过去了，价值衰减很快。后面整章上下文治理基本上都是围绕这件事展开的。

Function Calling 就是在这个基础上加的一层协议：把工具 Schema 写进 System，LLM 推理后只输出一段 tool_calls JSON，Harness 拿着 JSON 真正去执行，再把结果作为消息回灌。LLM 只产生意图，Harness 解析调用接口来行动。

## 第 13 页 · 上下文治理 · 问题与路径

ReAct 的本质决定了窗口必然会被工具结果不断挤占；到达高水位，模型出现幻觉、忘记方向的概率大大提高甚至不可用。
所以做了三重处理来治理上下文：分级压缩、优先级窗口、动态状态感知。

---

## 第 14 页 · 分级压缩 + 豁免

压缩分两级：
micro 把较早轮次的工具调用换成占位符，程序化操作，快且可控，每小轮 Agent Loop 触发；
auto 调 LLM 把整段历史摘要后清空再写回，彻底但贵且不可控，只在高水位触发。
这里有一个比较重要的设计——豁免机制：用户消息、Plan、TodoWrite、SubAgent 结论这些方向性消息不参与压缩，只压缩 Read、Bash、Edit 这种衰减极快的执行结果。

---

## 第 15 页 · 优先级窗口

传统的滑动窗口固定取最近 N 条消息，这会导致方向性消息容易被后来的执行消息挤出窗口。所以考虑给不同消息打上不同的价值优先级再按 3:6:1 的比例填窗——30% 给方向性消息、60% 给近期上下文、10% 给执行细节。最初考虑过背包问题，但是不能完全没有低价值的执行消息，否则 AI 容易进入 cosplay 环节，即凭空猜测但是不调用执行工具

---

## 第 16 页 · 动态状态感知

Agent 还需要知道"窗口外正在发生什么"。这里做了 System Prompt 和 messages 两层注入。
前者占位符每轮替换为后台任务、队友状态等实时快照；
后者则处理突发事件，用 `<system-reminder>` 消息软插入，不强行打断，让 Agent 在下一次小 Agent Loop 自然看到。

---

## 第 17 页 · 长程实测

这三层组合起来的效果，经过实测可以稳定跑到 2000 多轮消息窗口始终维持在健康水平、方向不跑偏。再配合指数退避来兜底偶发的 API 故障，理论上限会更高，这里只是取了运行比较长久的一个记录。

## 第 19 页 · 工具体系 · 渐进增强

工具这一部分的思路是渐进增强，面向场景适当增加工具。
理论上只要有 Read、Write、Bash、LoadSkill 这几个工具 Agent 便能工作
但适当增强工具，一定程度上能弥补模型能力，所以我给遇到的一些具体问题加了工具。下面选三个比较典型展开。

---

## 第 20 页 · Plan + 审批清空

第一个问题是 LLM 边想边改、调研读 30 个文件就把窗口撑大。我的做法是引入 Plan 工具，进入调研阶段给只读工具、产出计划文件
用户审批的时候顺便清空调研产物，保留计划文件。
窗口占用能从 65% 直接回到 12%，这样大幅缩减。

---

## 第 21 页 · 清空后执行

清空之后，工具集恢复完整，就可以对照计划文件逐步实施。代价是 Agent 忘掉了调研细节，但收益是执行阶段窗口干净，错误率明显下降，且方向性很强。

---

## 第 22 页 · Edit · 精确替换 + 凭证握手

Edit 工具我做了一些比较关键的增强。
一是基于 old_string 在文件中唯一匹配，匹配失败会给出诊断、匹配多次会提示加上下文。
二是批量替换的凭证握手：`replace_all` 不直接执行，先返回预览和文件摘要凭证
AI 确认无误把凭证回传然后执行；
好处是文件一变那么摘要凭证就失效，避免思考过程中文件变更导致的错误匹配替换。

---

## 第 23-24 页 · Bash 执行三态（合并讲）

Bash 这部分我是从一个真实卡死案例倒推出来的。
当时 Agent 跑一个常见 vite 模板的命令。这个命令是交互式的。
进程在等用户按回车、Agent 在等 命令的输出，陷入死锁。
所以给 Bash 命令引入了三个状态流转：命令执行超过预设时间，自动升级为后台运行，并且做做静默检测。
如果一直没有任何输出，那大概率就是在等用户输入，给 Agent 提示加 `-y`；如果还在出输出，就把进程移交后台、立即返回 task_id。
后续 Agent 凭借 task_id 可以调用 TaskOutput 工具等待结果，或 Session 工具操作标准输入输出处理交互

## 第 26 页 · 多 Agent · 两种模式

多 Agent 做了两种模式，分别以工具的方式呈现。
Teammate 是对等协作者，每个有独立窗口和工具集，通过共享聊天室广播沟通。
SubAgent 是临时的，独立窗口完全隔离，执行完只把一段精简摘要回灌给主 Agent——这样三个并行调研合计 70K token，主 Agent 只多用了 4%。

---

## 第 27 页 · 消息设计与可见性

为支撑这两种模式，消息层我做了三通道架构和信息不对称的可见性：
Main 看得到队友的文本和工具调用名，
Teammate 之间只看广播文本，
SubAgent 完全隔离
依据是决策信息多放、执行细节少放。

---

## 第 28-29 页 · 实验一 · 轮流报数（合并讲）

第一个实验是两个 Teammate 轮流报数，目的是验证消息传递与 Agent 触发，但实验暴露了一个没预想到的问题
过期快照导致重复消息：即，思考时间很长，导致期间新的消息和思考快照消息存在偏差，引起对外的不一致，这里说对外是对用户、对其他 Teammate
解决办法是 SendMessage 工具加一个二阶段提交门禁：
发消息之前先检查信箱有没有新消息，有就 hold 住、注入提醒、让 Agent 看到最新状态后再决策。
修复后 10 个数字全部正确报出、人工干预 0 次。

---

## 第 30 页 · 实验二 · 续写接龙

实验二把验证从"能按序发言"推进到"能否沿用同一组事实"。
就是多个 Teammate 轮流续写故事、保持人物时间线一致，逻辑自洽。
结果是 13 轮全部完成、偏题 0 次；只有 1 次内容重复，但符合逻辑预期

---

## 第 31 页 · 实验三 · 开发-测试协作

实验三是工程场景。
两个 Teammte 分别担任开发者和测试者去协作完成 45 项验收清单。
这里是出于 Anthropic 的文章指出模型对自己的工作有偏袒，让另一个 Agent 来评审才能拿到更客观反馈。
结果是第一轮 41 通过、4 项失败
开发队员 一次性修完
第二轮 45/45 全过；
需求完成率 100%、过程没有协同冲突

## 第 34 页 · 模板代码 · 问题

业务系统里有大量数据结构相关的高度模板化的代码。
经过实测：
让 LLM 逐字生成 51 张表的 DAO，结果漏了 11 个字段、4 个索引方法，烧了 24M token、跑了 53 分钟、压缩触发了 67 次。
这不是偶发错误，像是长链路推理的系统性风险。

---

## 第 35 页 · 核心观察

但仔细看这类代码会发现，它几乎不需要创造性决策：字段名直接映射、类型有固定对应、索引类型决定该有哪些查询方法。
即，DDL 已经是数据层代码的充分输入。那么考虑这部分就没必要让 LLM 来推理，交给确定性生成器更合适

---

## 第 36 页 · jen 架构

jen 的原理就四步：输入 schema、自研 parser 解析索引语义、用 Go template 渲染、输出按主键/唯一索引/普通索引派生的原子方法集。确定性输出、零字段漂移。

---

## 第 37 页 · jen 实测对比

同一份 schema 做对照实测，jen 把 token 降到了 1/50、耗时降到 1/27、字段一致性 100%。
引入模板生成代码的目的不是替代 Agent，是把规则稳定、容易漂移的部分从 LLM 链路里剥离出来，让模型可以专注在更有性价比的业务逻辑和契约定义上。

---

## 第 38 页 · webapp-gen 全栈工作流

把 jen 嵌进一个更大的流程，就是 webapp-gen。
webapp gen 是我固化的一条 11 步流水线：
模板脚手架前置 → 文档驱动定契约 → mock 原型反馈闭环 → jen 生成数据层 → 后端编码 → 三环境矩阵容器化验收。
这一个流程的主要考虑是接口和契约优先、从原型触发逐步填补完善系统
