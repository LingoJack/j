// part 01 · background

从 ChatBot 到 Agent：
谁在承担上下文成本？

ChatBot 时代

  • 人手动收集代码、报错日志、配置信息
  • 复制粘贴到对话窗口
  • AI 给出建议，人手动修改代码
  • 人承担上下文收集和执行反馈
  • 本质：人是物理世界和逻辑世界的桥梁
→

Agent 时代

  • Agent 通过工具主动读取代码、执行命令
  • Agent 自动管理上下文窗口
  • Agent 自主决策、自主执行、自主纠错
  • Agent 承担上下文治理和工具调用
  • 本质：Agent 成为桥梁，人被抽离出来

先从最根本的问题开始——ChatBot 和 Agent 的区别到底是什么？

大家回想一下 2023、2024 年用 GPT 的场景。我们有 bug，需要自己去收集代码、报错日志、运行环境信息，然后复制粘贴到 ChatBot 里，ChatBot 给出建议，我们再自己去改代码。

这个过程里，人承担了两个关键角色：上下文收集者和物理世界与逻辑世界的桥梁。"物理世界"就是你的代码、文件系统、终端；"逻辑世界"就是 LLM 的思考空间。

而 Agent 的核心转变就是：通过上下文窗口的治理和工具的使用，Agent 自己承担了这些角色，人被抽离了出来。

但这带来一个新的挑战——Agent 怎么在一个有限的上下文窗口里，长期稳定地工作？这就是我整个毕设要解决的核心问题。

每一轮 Tool Call 的结果都会被解析、序列化、塞回上下文窗口——窗口越填越满，这就是后面所有问题的源头。

#react #thought-action-observation

讲 Agent 之前，必须先讲清楚它怎么运转的。Agent 的心脏，就是这个 ReAct 循环——Reasoning + Acting 的简称。

每一轮，Agent 先做 Thought，看着当前上下文窗口里的内容思考"我下一步该干什么"。然后做 Action——按照工具的 JSON Schema 格式生成一个 Tool Call。

这个 Tool Call 会被我们的运行时拿去真正执行——可能是读一个文件、可能是跑一条 Bash 命令、可能是搜代码。执行的结果就是 Observation，我们把这个结果解析、序列化，再塞回上下文窗口。

然后 Agent 看到这个新的窗口内容，进入下一轮 Thought。如此循环。

这里有一个非常关键的副作用——每一轮工具结果都在占用窗口空间。一个文件可能上千行，一个搜索结果可能十几个匹配。跑十几轮之后，窗口就满了。这就是我后面所有上下文治理工作的问题源头。

// part 02 · context window

核心挑战：上下文窗口有限

Problem

LLM 的上下文窗口有硬上限（如 128K tokens）。Agent 执行一次复杂任务可能涉及数十次工具调用，每次调用结果都会填充窗口。

窗口一旦满了，Agent 就会丢失早期关键信息，导致幻觉、重复操作、忘记目标。

Solution

设计分级消息窗口和滚动窗口机制，智能地决定哪些信息保留、哪些压缩、哪些丢弃。

类比推荐系统：把最有价值的上下文信息装入窗口，低价值执行过程少放，决策信息多放。

#context-window #scrolling

现在进入第二部分，整个项目最核心的设计——上下文窗口治理。

问题很直接：LLM 的上下文窗口有硬上限，比如 128K tokens。但 Agent 执行一次复杂任务，可能要调用几十次工具，每次工具返回的结果都会往窗口里塞内容。窗口一满，早期的关键信息就丢了。

信息丢了会怎样？Agent 开始幻觉——编造不存在的函数名；开始重复操作——又去读一遍已经读过的文件；开始忘记目标——用户让它改 A，它改到一半跑去改 B。

怎么解决？我设计了一套分级消息窗口 + 滚动窗口的机制。核心思想很像推荐系统——窗口空间有限，我们把最有价值的信息优先塞进去。什么是高价值的？用户消息、Agent 的决策信息、Plan 计划文档——这些是指导方向的。什么是低价值的？工具执行的中间过程、大段文件内容——这些信息随着轮次推进，价值快速衰减。

#token-pressure #hallucination

给大家直观感受一下，不治理会发生什么。这是我跑一个真实任务的窗口占用变化。

第一轮，刚发完用户需求，窗口才 18%——风平浪静。第二轮，Agent 用 Glob 扫了项目结构，又 Read 了几个主文件，已经到 38%。

第三轮是关键转折——Agent 开始大量 Grep 搜索 + 读相关文件，因为它要建立项目理解。每个 Read 都是几千个 token，五个文件就是上万。窗口冲到 62%。

第四轮跑了 cargo build，编译错误日志几百行，Edit 又产生了 diff，已经 84%。

第五轮，97% ——这是危险区。Agent 开始幻觉，开始重复读已经读过的文件，开始忘记最初的需求。

这时候我们的 auto compact 触发——把对话历史总结成精简摘要，清空窗口重写。窗口回到 34%，关键决策保留。Agent 又能继续高效工作。

这个曲线是真实跑出来的，不是画的示意。

// part 02 · compaction

多级压缩：micro 与 auto

豁免
高价值消息不被压缩

用户消息、Agent 语言消息、System 提醒（TODO/Teammate）、Plan、Skill、TODOWrite/Read、SubAgent 结果 —— 这些是决策和方向信息，必须保留。

micro
轻量级压缩 —— 快速腾出空间

保留消息摘要和关键结论，去除冗长的工具输出。速度快，适合窗口接近上限时快速释放空间。

auto
深度压缩 —— 完整重写窗口

将整个对话历史总结为精简摘要，然后清空窗口 + 写入摘要。适合 Agent 已经运行很久，需要一次"大扫除"的场景。

* Read/Edit/Bash 等工具调用结果不豁免，因为其信息价值随轮次衰减极快。

压缩系统是上下文治理的核心实现。分三个层面来讲。

首先，豁免机制。不是所有消息都能压缩——有些信息一旦丢失，Agent 就彻底跑偏了。我把这些消息标记为"豁免"：用户消息（这是需求源头）、Agent 的语言消息（这是决策记录）、System 提醒（TODO、Teammate 状态这些）、Plan 文档、Skill 内容、TODOWrite/Read（任务追踪）、SubAgent 的最终结果。

反过来，像 Read、Edit、Bash 这些工具的调用结果，我不豁免。为什么？因为一个文件被读过的内容，在第 20 轮对话的时候，对 Agent 决策的价值已经非常低了。它的信息价值随轮次衰减极快。

然后是两级压缩。micro 级别做轻量摘要，速度快，适合窗口快满时快速释放空间。auto 级别做深度压缩——把整个对话历史总结成一段精简摘要，然后清空窗口重新开始。这样兼顾了速度和准确率，让 Agent 可以长期健康运行，大大降低了幻觉。

核心洞察：决策信息多放、指导方向信息多放、执行中间过程信息少放

#scrolling-window #rec-sys-analogy

这里我想分享一个比较有意思的跨领域类比——上下文窗口治理和推荐系统非常像。

推荐系统是什么？给定有限的展示位，从大量候选物料里挑出最值得展示的几个，按价值排序。上下文窗口治理是什么？给定有限的 token 配额，从大量历史消息里挑出最值得保留的几条，按价值塞入。

所以我设计了一套价值评分机制。左边是候选池——所有历史消息按"对未来决策的价值"打分。高价值消息：用户需求、Plan 文档、Agent 自己的决策语句、当前 TODO、SubAgent 的调研结论——这些是"指导方向"的信息。低价值消息：远期的 Bash 输出、中间过程的 Grep 结果、已经被覆盖的旧 Edit——这些是"执行中间过程"，价值衰减快。

排序器按价值降序填窗口，高分必保留，低分被丢弃。这就是我说的"决策信息多放、指导方向信息多放、执行中间过程信息少放"。

另一个关键设计是动态 System Prompt。System Prompt 不是一成不变的——它的尾部会根据当前状态动态追加信息。

基础部分是静态的：项目规范（比如 AGENTS.md 里定义的代码规范）、工具定义、环境信息、按需加载的 Skill 内容。

动态部分才是关键。当 Agent 之前启动了一个后台任务，但工具调用记录已经被压缩掉了，Agent 怎么知道这个任务还在跑？靠的就是System Prompt 尾部动态追加的后台任务状态。同样的机制还用于：Teammate 的存在和状态、很久没更新过的 TODO 项目的提醒、当前正在进行的交互式 Session。

这个设计的核心思路是：让 Agent 感知当前正在发生的持续性事件，即使这些事件的原始上下文已经被压缩了。

现在进入第三部分——工具体系。我的设计哲学是渐进增强：从最基础的几个工具开始，每个新工具的引入都是为了解决前面遇到的特定问题。

最底层是基础层：Read、Write、Bash、LoadSkill。有了这四个工具，Agent 理论上就能工作了——能读文件、写文件、执行命令。但实际上远远不够。

第二层是增强层。每个工具都有明确的引入动机：Grep 让 Agent 面对未知项目时能高效搜索，比用 Bash grep 质量稳定得多；Ask 给用户一个澄清意图的入口，避免做出来的东西跟预期漂移；Plan 帮 Agent 提前想清楚再动手，减少改不全的问题；WebFetch/Search 增强 Agent 获取最新知识的能力。

第三层是协作层：TodoWrite/Read 帮 Agent 追踪进度、避免遗漏；SubAgent 委派调研任务以低成本收集上下文；Teammate 实现多 Agent 协作；Session 处理交互式命令。

// part 03 · why new tools

为什么需要 Grep 和 Ask？

Grep：构建上下文的关键工具

面对一个未知的项目，Agent 需要主动搜索代码来构建上下文。

没有 Grep：Agent 只能通过 Bash 执行 grep 命令，匹配质量不稳定、输出格式难解析、速度慢。

有了 Grep：结构化搜索结果，支持正则、文件类型过滤、上下文行数、分页。Agent 能高效定位目标代码。

Ask：防止需求漂移的阀门

用户的需求描述往往模糊或不完整，Agent 如果盲目执行，最终产物可能与用户预期严重漂移。

没有 Ask：Agent 猜测意图，做完后发现不是用户想要的，返工成本高。

有了 Ask：Agent 可以在关键决策点征询用户意见，扩展明确需求，避免方向性错误。

我挑两个典型工具展开讲一下，说明每个工具引入背后的问题驱动思路。

先说 Grep。Agent 面对一个从来没见过的项目，它怎么知道代码在哪？它需要搜索。没有 Grep 工具的时候，Agent 只能通过 Bash 执行 shell 的 grep 命令。但 shell grep 的输出格式不稳定，Agent 解析起来容易出错，而且缺乏上下文行、文件类型过滤等高级功能。

有了专用的 Grep 工具，搜索结果是结构化的——带行号、带上下文、支持正则、支持文件类型过滤。Agent 能快速定位到目标代码，这是它主动构建上下文的关键能力。

再说 Ask。用户说"帮我做一个好看的页面"，这需求太模糊了。如果 Agent 不问就直接做，做完发现用户要的是红色风格，Agent 做了个蓝色的——这就是需求漂移。Ask 工具让 Agent 在不确定的时候主动向用户确认，在关键决策点征询意见。一个简单的确认，可能省掉几个小时的返工。

// part 03 · plan & edit

Plan + Edit：想清楚再动手

P
Plan 工具：先调研，再规划，后执行

问题：LLM 有时候没想清楚就开始改代码，导致变更不完整、改了 A 漏了 B，且调研过程占用大量上下文。

方案：进入 Plan 模式 → 只读调研（Read/Grep/Glob）→ 制定自包含执行计划 → 清空上下文 → 按计划执行。调研信息不污染执行阶段窗口。

E
Edit 工具：精确替换，非全文覆写

问题：Write 工具只能全文覆写文件，对大文件的微小改动效率极低，且容易引入意外修改。

方案：Edit 工具基于精确字符串匹配做局部替换，只发送 diff 而非全文，大幅减少 token 消耗和错误率。

接下来讲两个对编码场景特别关键的工具。

Plan 工具解决的问题是：LLM 经常没想清楚就开始动手。比如用户说"把这个函数重构一下"，Agent 直接去改代码，改了三处漏了两处，最后还不如不改。

Plan 的设计是：先进入一个只读调研模式——只能用 Read、Grep、Glob 这些工具去了解项目。调研完之后，制定一个完整的执行计划。然后做一个关键操作——清空上下文。调研阶段读了几十个文件，这些信息占了很多窗口空间，但真正执行的时候用不到那么多。清空之后，只把计划文档写进去，Agent 就能在干净的窗口里按计划高效执行。

Edit 工具解决的是 Write 工具的粗粒度问题。Write 只能全文覆写，但如果一个文件有 500 行，你只改第 200 行的一个函数名，用 Write 就要把 500 行全部发给 LLM 再全部写回来。Edit 只需要指定"把这段旧字符串替换成这段新字符串"，精确、高效、不容易出错。

调研过程读了 30 个文件，把窗口塞满。开始改代码时窗口已经无空间，Agent 改完 A 漏了 B、忘了用户的原始约束。

正例 · 有 Plan

调研窗口被丢弃，执行窗口干净。Plan 文档承载所有调研结论，变更可追溯、不漂移。

#plan #clear-and-approve

Plan 工具不只是"先想再做"，它的核心机制是三阶段 + 中间清空。这一页详细讲讲。

第一阶段，调研。Agent 进入只读模式，能用的工具受限——只有 Read、Grep、Glob、WebFetch 这些不修改任何东西的工具。这个阶段它做的事是建立对项目的完整理解。

第二阶段，计划 + 审批。Agent 把调研结论写成一份自包含的 Plan.md——明确写出每一步要改哪个文件、加什么函数、删什么逻辑。用户看 Plan，确认方向对，approve。

第三阶段是关键——上下文清空。调研阶段读的 30 个文件、几万 token 的内容，全部丢弃。只把 Plan 文档保留下来。Agent 在一个干净的窗口里，对照 Plan 一步步执行。

这样做的好处太明显了——执行阶段不再被调研垃圾信息干扰，Plan 还能作为变更文档留下来追溯。这是 idea 里说的"clear and approval"机制。

AI 执行命令的时候，会遇到三种场景，所以我设计了三种执行形态。

第一种是同步 Bash——执行一条快命令，比如 ls、cargo build，等它跑完返回结果就行。

但有些命令会跑很久，比如 npm install 可能耗时几分钟。这时候如果 Bash 超过预设的 timeout，它就会自动流转为后台任务。Agent 不需要提前预判这个命令会不会跑很久——它会自动升级。后台任务可以通过 TaskOutput 非阻塞地获取当前状态和产物。

第三种是Session——有些命令是交互式的，比如安装 React 框架模板时会问你"确认安装吗？"需要输入 y。为了处理这种场景，我把命令的 stdin/stdout 打通，封装为一个独立的 Session 工具。Agent 可以通过 Session 发送输入、读取输出，完成交互操作。

这三种形态覆盖了 Agent 执行命令的几乎所有场景，而且流转是自动的，Agent 不用操心。

#2pc #message-inbox

讲一个比较工程化的细节——Two-Staged Commit。这个问题大家可能不直观，我先描述一下场景。

因为 Agent Loop 是长时序异步的——Agent 发完一条消息之后，自己继续往下跑，但消息可能因为网络抖动、广播延迟没有立即送达。Agent 在下一轮看不到自己刚发的消息，会以为"上次发失败了"，再发一遍。结果用户看到同样的话重复三次，体验极差。

我设计的解决方案是两阶段提交。SendMessage 工具调用的时候，消息先进入 Inbox 的 pending 状态——这是第一阶段。然后由专门的提交器做第二阶段 commit，把状态变为 committed，这时候才对其他 Agent 和 UI 可见。

这个设计的双重好处是——对外，整个 Agent Team 系统给用户的体验是一致的，没有重复消息；对内，重复的消息也不会进入其他 Agent 的上下文窗口，避免了 token 浪费和决策干扰。

SubAgent 和 Teammate 不一样——Teammate 是平等的协作者，SubAgent 是临时雇用的调研员。

核心思想是上下文隔离。主 Agent 想要了解一个未知模块，如果自己去 Read 十几个文件，主窗口会被瞬间填满几十 K token。这些原始内容里 90% 都是噪音，主 Agent 真正需要的只是一段结论。

所以我设计了 SubAgent 工具——主 Agent 派一个 SubAgent 去做调研，SubAgent 在自己独立的上下文窗口里读文件、搜代码、跑工具。调研完了，SubAgent 只把最终摘要结论回灌给主 Agent。

你看这张图——三个 SubAgent 并行调研，每个用掉 20-30K tokens 的独立窗口。但主 Agent 收到的只是三段总计 1.5K 的摘要。主窗口仅微增 4%，但主 Agent 获得了三个模块的完整理解。

这就是"以较低的上下文成本了解调研目标"——也是 SubAgent 这个抽象最大的价值。

// part 04 · robustness

健壮性设计：错误处理与 Hook 系统

指数退避重试

大模型 API 调用不可避免会遇到网络错误、限流、超时等问题。

采用指数退避（Exponential Backoff）机制：第一次重试等 1 秒，第二次等 2 秒，第三次等 4 秒……自动处理瞬态故障，无需人工干预。

Hook 系统

用作回归测试和工程规范强制执行：

  • 禁止使用 mod.rs，强制 name.rs + name/ 模式
  • 禁止可能导致 panic 的 unwrap() / expect()
  • 变更内容必须沉淀为文档
  • 代码必须通过 cargo fmt 和 clippy

工程上还有一些健壮性设计，也值得提一下。

指数退避重试。调用大模型 API 不是每次都成功的——网络会断、会被限流、会超时。如果 Agent 遇到一次错误就停下来等人工处理，那它的自主性就打了折扣。所以我实现了指数退避：第一次重试等 1 秒，第二次 2 秒，第三次 4 秒，以此类推。大多数瞬态故障都能自动恢复。

Hook 系统。这是代码质量的守护者。我在项目中定义了一系列规则，通过 Hook 在代码提交或文件变更时自动检查。比如：禁止用 mod.rs，我们要求 name.rs + name/ 的文件组织方式；禁止使用可能导致 panic 的 unwrap()；变更内容必须写文档方便后续维护。这些 Hook 确保了 Agent 生成的代码符合工程规范。

TodoWrite/TodoRead

Agent 在开始大任务前列出所有子任务。每完成一个就更新状态。避免遗漏变更、避免忘记目标。

system_reminder 注入

Agent: <读了 5 个文件，跑了 3 次 grep…>
system_reminder:

Currently in_progress: "改 handler/tui_loop.rs 调用点"

#todo #system-reminder

讲一个特别有用的小工具——TodoWrite + system_reminder。这看着简单，但对 Agent 长期运行有奇效。

问题是这样的：Agent 跑一个大任务，可能要改十几个文件。如果它没有显式的待办清单，跑着跑着就忘记原本要做的事。改了两个就觉得任务完成了，剩下的就漏了。

所以我让 Agent 在开始大任务前先列出所有 TODO 项。每完成一个就更新状态。这本身就强迫它把任务结构化拆分。

但还有个更巧妙的设计——system_reminder 注入。如果 Agent 连续好几轮都没更新 TODO，但 TODO 里还有 in_progress 项，系统就会在下一轮 prompt 尾部注入一条 system_reminder：「你还有 4 个 TODO，其中一个 in_progress 已经 8 轮没动了，是不是该看看？」

这相当于一个软中断——不强行打断 Agent，但在它注意力分散的时候轻轻拉一下。实测对完成度提升非常明显。

Hook 系统是 Agent 真正能"用于生产"的关键。它把工程规范固化成自动执行的脚本，跑在 Agent 整个生命周期的各个事件点上。

第二个例子是 webapp-gen——一个 Web App 生成工作流。它的策略是"原型驱动，逐步填充"——先搭出完整的项目骨架和基础页面，确保项目结构没问题，然后再根据用户需求逐步填充替换。这比"一口气生成完整应用"靠谱得多。

核心优势：项目结构完整性有脚手架保证；用户预期通过逐步可见的原型校准，减少"做完发现不对"的反工。

#webapp-gen #prototype-driven

Skill 系统的第二个深入案例是 webapp-gen——生成完整 Web App 的工作流。

先讲一个常见的反例。用户说"帮我做个待办应用"，AI 抖擞精神一口气生成 50 个文件。结果是什么？路由配置漏写一行、CSS 路径引错、组件 import 出现循环依赖。项目跑不起来。用户又得逐个排查。

问题在哪？大模型不擅长一次性产出结构完整的工程。文件越多，遗漏的概率越高。

所以我设计了原型驱动的工作流。第一步，用成熟的脚手架——比如 vite + react + tailwind 模板——搭出一个可以立即 run 起来的最小项目。这个项目已经有路由、状态、样式系统，工程结构完整。

第二步，逐页用 mock 数据填充原型。用户能看到"应用大概长什么样"，可以提前给视觉反馈，减少方向漂移。

第三步，把 mock 替换为真实 API，逐步加入业务逻辑。每一步都是增量改造，可见、可控、可回退。

这就是"原型驱动、逐步填充"——既保住项目完整性，又匹配用户预期。

总结：三个核心贡献

上下文窗口治理

分级消息窗口 + 多级压缩（micro/auto）+ 动态 System Prompt 追加。让 Agent 能在有限窗口内长期稳定运行，大幅降低幻觉和重复操作。

渐进式工具体系

从 4 个基础工具到 20+ 工具，每个工具都有明确的问题驱动动机。Plan 清空上下文、Grep 构建上下文、Ask 防漂移、Session 处理交互——形成完整闭环。

多 Agent 协作

Teammate/SubAgent 协作 + Two-Staged Commit 消息一致性 + 交叉评审客观评估 + 指数退避健壮性。Agent 团队能长期高效协作。

github.com/LingoJack/jcli

好，做个总结。我这个毕设的核心贡献有三个。

第一，上下文窗口治理。这是最核心的。分级消息窗口决定哪些信息优先保留，多级压缩在窗口快满时智能释放空间，动态 System Prompt 让 Agent 感知持续状态。三者配合，Agent 能在有限窗口内长期稳定运行，幻觉和重复操作大幅降低。

第二，渐进式工具体系。从 4 个基础工具扩展到 20 多个，每个新工具都是为了解决前面遇到的特定问题。Plan 帮助清空上下文重新出发，Grep 帮助高效构建上下文，Ask 防止需求漂移，Session 处理交互式命令。这些工具形成了一个完整的闭环。

第三，多 Agent 协作。通过 Teammate 和 SubAgent 实现 Agent 团队协作，用 Two-Staged Commit 保证消息一致性，用交叉评审实现客观质量评估，用指数退避增强健壮性。
