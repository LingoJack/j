// part 01 · background

从 ChatBot 到 Agent：
谁在承担上下文成本？

ChatBot 时代

  • 人手动收集代码、报错日志、配置信息
  • 复制粘贴到对话窗口
  • AI 给出建议，人手动修改代码
  • 人承担上下文收集和执行反馈
  • 本质：人是物理世界和逻辑世界的桥梁
→

Agent 时代

  • Agent 通过工具主动读取代码、执行命令
  • Agent 自动管理上下文窗口
  • Agent 自主决策、自主执行、自主纠错
  • Agent 承担上下文治理和工具调用
  • 本质：Agent 成为桥梁，人被抽离出来

先从最根本的问题开始——ChatBot 和 Agent 的区别到底是什么？

大家回想一下 2023、2024 年用 GPT 的场景。我们有 bug，需要自己去收集代码、报错日志、运行环境信息，然后复制粘贴到 ChatBot 里，ChatBot 给出建议，我们再自己去改代码。

这个过程里，人承担了两个关键角色：上下文收集者和物理世界与逻辑世界的桥梁。"物理世界"就是你的代码、文件系统、终端；"逻辑世界"就是 LLM 的思考空间。

而 Agent 的核心转变就是：通过上下文窗口的治理和工具的使用，Agent 自己承担了这些角色，人被抽离了出来。

但这带来一个新的挑战——Agent 怎么在一个有限的上下文窗口里，长期稳定地工作？这就是我整个毕设要解决的核心问题。

// part 02 · context window

核心挑战：上下文窗口有限

Problem

LLM 的上下文窗口有硬上限（如 128K tokens）。Agent 执行一次复杂任务可能涉及数十次工具调用，每次调用结果都会填充窗口。

窗口一旦满了，Agent 就会丢失早期关键信息，导致幻觉、重复操作、忘记目标。

Solution

设计分级消息窗口和滚动窗口机制，智能地决定哪些信息保留、哪些压缩、哪些丢弃。

类比推荐系统：把最有价值的上下文信息装入窗口，低价值执行过程少放，决策信息多放。

#context-window #scrolling

现在进入第二部分，整个项目最核心的设计——上下文窗口治理。

问题很直接：LLM 的上下文窗口有硬上限，比如 128K tokens。但 Agent 执行一次复杂任务，可能要调用几十次工具，每次工具返回的结果都会往窗口里塞内容。窗口一满，早期的关键信息就丢了。

信息丢了会怎样？Agent 开始幻觉——编造不存在的函数名；开始重复操作——又去读一遍已经读过的文件；开始忘记目标——用户让它改 A，它改到一半跑去改 B。

怎么解决？我设计了一套分级消息窗口 + 滚动窗口的机制。核心思想很像推荐系统——窗口空间有限，我们把最有价值的信息优先塞进去。什么是高价值的？用户消息、Agent 的决策信息、Plan 计划文档——这些是指导方向的。什么是低价值的？工具执行的中间过程、大段文件内容——这些信息随着轮次推进，价值快速衰减。

// part 02 · compaction

多级压缩：micro 与 auto

豁免
高价值消息不被压缩

用户消息、Agent 语言消息、System 提醒（TODO/Teammate）、Plan、Skill、TODOWrite/Read、SubAgent 结果 —— 这些是决策和方向信息，必须保留。

micro
轻量级压缩 —— 快速腾出空间

保留消息摘要和关键结论，去除冗长的工具输出。速度快，适合窗口接近上限时快速释放空间。

auto
深度压缩 —— 完整重写窗口

将整个对话历史总结为精简摘要，然后清空窗口 + 写入摘要。适合 Agent 已经运行很久，需要一次"大扫除"的场景。

* Read/Edit/Bash 等工具调用结果不豁免，因为其信息价值随轮次衰减极快。

压缩系统是上下文治理的核心实现。分三个层面来讲。

首先，豁免机制。不是所有消息都能压缩——有些信息一旦丢失，Agent 就彻底跑偏了。我把这些消息标记为"豁免"：用户消息（这是需求源头）、Agent 的语言消息（这是决策记录）、System 提醒（TODO、Teammate 状态这些）、Plan 文档、Skill 内容、TODOWrite/Read（任务追踪）、SubAgent 的最终结果。

反过来，像 Read、Edit、Bash 这些工具的调用结果，我不豁免。为什么？因为一个文件被读过的内容，在第 20 轮对话的时候，对 Agent 决策的价值已经非常低了。它的信息价值随轮次衰减极快。

然后是两级压缩。micro 级别做轻量摘要，速度快，适合窗口快满时快速释放空间。auto 级别做深度压缩——把整个对话历史总结成一段精简摘要，然后清空窗口重新开始。这样兼顾了速度和准确率，让 Agent 可以长期健康运行，大大降低了幻觉。

另一个关键设计是动态 System Prompt。System Prompt 不是一成不变的——它的尾部会根据当前状态动态追加信息。

基础部分是静态的：项目规范（比如 AGENTS.md 里定义的代码规范）、工具定义、环境信息、按需加载的 Skill 内容。

动态部分才是关键。当 Agent 之前启动了一个后台任务，但工具调用记录已经被压缩掉了，Agent 怎么知道这个任务还在跑？靠的就是System Prompt 尾部动态追加的后台任务状态。同样的机制还用于：Teammate 的存在和状态、很久没更新过的 TODO 项目的提醒、当前正在进行的交互式 Session。

这个设计的核心思路是：让 Agent 感知当前正在发生的持续性事件，即使这些事件的原始上下文已经被压缩了。

现在进入第三部分——工具体系。我的设计哲学是渐进增强：从最基础的几个工具开始，每个新工具的引入都是为了解决前面遇到的特定问题。

最底层是基础层：Read、Write、Bash、LoadSkill。有了这四个工具，Agent 理论上就能工作了——能读文件、写文件、执行命令。但实际上远远不够。

第二层是增强层。每个工具都有明确的引入动机：Grep 让 Agent 面对未知项目时能高效搜索，比用 Bash grep 质量稳定得多；Ask 给用户一个澄清意图的入口，避免做出来的东西跟预期漂移；Plan 帮 Agent 提前想清楚再动手，减少改不全的问题；WebFetch/Search 增强 Agent 获取最新知识的能力。

第三层是协作层：TodoWrite/Read 帮 Agent 追踪进度、避免遗漏；SubAgent 委派调研任务以低成本收集上下文；Teammate 实现多 Agent 协作；Session 处理交互式命令。

// part 03 · why new tools

为什么需要 Grep 和 Ask？

🔍 Grep：构建上下文的关键工具

面对一个未知的项目，Agent 需要主动搜索代码来构建上下文。

没有 Grep：Agent 只能通过 Bash 执行 grep 命令，匹配质量不稳定、输出格式难解析、速度慢。

有了 Grep：结构化搜索结果，支持正则、文件类型过滤、上下文行数、分页。Agent 能高效定位目标代码。

❓ Ask：防止需求漂移的阀门

用户的需求描述往往模糊或不完整，Agent 如果盲目执行，最终产物可能与用户预期严重漂移。

没有 Ask：Agent 猜测意图，做完后发现不是用户想要的，返工成本高。

有了 Ask：Agent 可以在关键决策点征询用户意见，扩展明确需求，避免方向性错误。

我挑两个典型工具展开讲一下，说明每个工具引入背后的问题驱动思路。

先说 Grep。Agent 面对一个从来没见过的项目，它怎么知道代码在哪？它需要搜索。没有 Grep 工具的时候，Agent 只能通过 Bash 执行 shell 的 grep 命令。但 shell grep 的输出格式不稳定，Agent 解析起来容易出错，而且缺乏上下文行、文件类型过滤等高级功能。

有了专用的 Grep 工具，搜索结果是结构化的——带行号、带上下文、支持正则、支持文件类型过滤。Agent 能快速定位到目标代码，这是它主动构建上下文的关键能力。

再说 Ask。用户说"帮我做一个好看的页面"，这需求太模糊了。如果 Agent 不问就直接做，做完发现用户要的是红色风格，Agent 做了个蓝色的——这就是需求漂移。Ask 工具让 Agent 在不确定的时候主动向用户确认，在关键决策点征询意见。一个简单的确认，可能省掉几个小时的返工。

// part 03 · plan & edit

Plan + Edit：想清楚再动手

P
Plan 工具：先调研，再规划，后执行

问题：LLM 有时候没想清楚就开始改代码，导致变更不完整、改了 A 漏了 B，且调研过程占用大量上下文。

方案：进入 Plan 模式 → 只读调研（Read/Grep/Glob）→ 制定自包含执行计划 → 清空上下文 → 按计划执行。调研信息不污染执行阶段窗口。

E
Edit 工具：精确替换，非全文覆写

问题：Write 工具只能全文覆写文件，对大文件的微小改动效率极低，且容易引入意外修改。

方案：Edit 工具基于精确字符串匹配做局部替换，只发送 diff 而非全文，大幅减少 token 消耗和错误率。

接下来讲两个对编码场景特别关键的工具。

Plan 工具解决的问题是：LLM 经常没想清楚就开始动手。比如用户说"把这个函数重构一下"，Agent 直接去改代码，改了三处漏了两处，最后还不如不改。

Plan 的设计是：先进入一个只读调研模式——只能用 Read、Grep、Glob 这些工具去了解项目。调研完之后，制定一个完整的执行计划。然后做一个关键操作——清空上下文。调研阶段读了几十个文件，这些信息占了很多窗口空间，但真正执行的时候用不到那么多。清空之后，只把计划文档写进去，Agent 就能在干净的窗口里按计划高效执行。

Edit 工具解决的是 Write 工具的粗粒度问题。Write 只能全文覆写，但如果一个文件有 500 行，你只改第 200 行的一个函数名，用 Write 就要把 500 行全部发给 LLM 再全部写回来。Edit 只需要指定"把这段旧字符串替换成这段新字符串"，精确、高效、不容易出错。

stdin/stdout 双向通道

自动流转：Bash 超时自动升级为后台任务，Agent 无需预判命令是否会耗时。

交互能力：npm install 需要 y 确认？Session 工具打通 stdin/stdout，支持实时交互。

结果获取：TaskOutput 非阻塞检查任务状态，完成即取，未完成则继续等待。

AI 执行命令的时候，会遇到三种场景，所以我设计了三种执行形态。

第一种是同步 Bash——执行一条快命令，比如 ls、cargo build，等它跑完返回结果就行。

但有些命令会跑很久，比如 npm install 可能耗时几分钟。这时候如果 Bash 超过预设的 timeout，它就会自动流转为后台任务。Agent 不需要提前预判这个命令会不会跑很久——它会自动升级。后台任务可以通过 TaskOutput 非阻塞地获取当前状态和产物。

第三种是Session——有些命令是交互式的，比如安装 React 框架模板时会问你"确认安装吗？"需要输入 y。为了处理这种场景，我把命令的 stdin/stdout 打通，封装为一个独立的 Session 工具。Agent 可以通过 Session 发送输入、读取输出，完成交互操作。

这三种形态覆盖了 Agent 执行命令的几乎所有场景，而且流转是自动的，Agent 不用操心。

// part 04 · multi-agent

多 Agent 协作：
聊天室 + 客观评估

①
Teammate

独立 Agent 实例，各有专属上下文和工具，通过 SendMessage 广播 + @提及 通信。

②
SubAgent

临时子 Agent，用于委派调研任务或并行开发。主 Agent 只可见最终结果，以低上下文成本获取信息。

③
Two-Staged Commit

SendMessage + Message Inbox 的两阶段提交机制，解决 Agent Loop 长时序导致的重复消息问题。

④
客观评估

参考 Anthropic 的研究——模型倾向偏袒自己的工作。通过聊天室让其他 Agent 交叉评审，实现相对客观的质量评估。

第四部分，多 Agent 协作。这是让 Agent 能处理复杂任务的关键能力。

Teammate 是独立的 Agent 实例，每个都有自己专属的上下文和工具集。它们通过 SendMessage 工具在聊天室里广播消息，可以用 @提及 来定向通信。

SubAgent 是一种轻量级的子 Agent，主要用来做两件事：一是调研——让 SubAgent 去搜索、阅读、收集信息，主 Agent 只需要看最终的调研结果，不需要消耗自己的上下文去遍历文件；二是并行开发——多个 SubAgent 同时工作，提高效率。

这里有个重要的工程问题——Two-Staged Commit。因为 Agent Loop 是长时序的，两个 Agent 可能同时往聊天室发消息，导致重复或冲突。我设计了发送 + 确认的两阶段提交机制，确保消息的一致性。

还有一个很有意思的设计是客观评估。Anthropic 有一篇研究指出，LLM 倾向于对自己的工作感到满意——"我做的挺好的"。通过聊天室让其他 Agent 来评审，就能实现相对客观的质量评估。

// part 04 · robustness

健壮性设计：错误处理与 Hook 系统

🔄 指数退避重试

大模型 API 调用不可避免会遇到网络错误、限流、超时等问题。

采用指数退避（Exponential Backoff）机制：第一次重试等 1 秒，第二次等 2 秒，第三次等 4 秒……自动处理瞬态故障，无需人工干预。

🪝 Hook 系统

用作回归测试和工程规范强制执行：

  • 禁止使用 mod.rs，强制 name.rs + name/ 模式
  • 禁止可能导致 panic 的 unwrap() / expect()
  • 变更内容必须沉淀为文档
  • 代码必须通过 cargo fmt 和 clippy

工程上还有一些健壮性设计，也值得提一下。

指数退避重试。调用大模型 API 不是每次都成功的——网络会断、会被限流、会超时。如果 Agent 遇到一次错误就停下来等人工处理，那它的自主性就打了折扣。所以我实现了指数退避：第一次重试等 1 秒，第二次 2 秒，第三次 4 秒，以此类推。大多数瞬态故障都能自动恢复。

Hook 系统。这是代码质量的守护者。我在项目中定义了一系列规则，通过 Hook 在代码提交或文件变更时自动检查。比如：禁止用 mod.rs，我们要求 name.rs + name/ 的文件组织方式；禁止使用可能导致 panic 的 unwrap()；变更内容必须写文档方便后续维护。这些 Hook 确保了 Agent 生成的代码符合工程规范。

// part 05 · skill system

Skill 系统：工程化能力的按需封装

🏗️ jen — SQL → Go 代码生成

自研 SQL 语法解析器 + 模板引擎，自动生成 DAO 层和 Model 层代码。

为什么不直接用 AI 生成？DAO/Model 代码高度模板化、体量大，AI 生成质量不稳定且耗时。工程化生成则质量可控、速度快、不侵入业务逻辑。

为什么封装为 Skill？按需加载，非必要不占用上下文。只在遇到 SQL 相关场景时才激活。

🌐 webapp-gen — Web App 生成

内含脚手架工具和完整工作流。

核心策略：原型驱动，逐步填充。先用脚手架搭出项目骨架和基础页面，再根据用户需求逐步替换和填充内容。

优势：保证项目结构完整性的同时，逐步逼近用户预期，减少"做完发现不对"的风险。

最后讲一个重要的工程化设计——Skill 系统。

Skill 的核心理念是按需加载。不是把所有能力都塞进 System Prompt，而是只有当 Agent 遇到特定场景时，才通过 LoadSkill 工具加载对应的技能包。

第一个例子是 jen——一个从 SQL 语句自动生成 Go 结构体和 DAO 层代码的工具。它的核心是我开发的一个 SQL 语法解析器，能从 SQL 里提取出表名、字段、索引等关键信息，然后基于模板语法生成完整的 CRUD 方法、事务方法、条件查询等。为什么不用 AI 直接生成？因为 DAO/Model 代码太模板化了，AI 生成容易出错还慢，工程化生成质量可控。

第二个例子是 webapp-gen——一个 Web App 生成工作流。它的策略是"原型驱动，逐步填充"——先搭出完整的项目骨架和基础页面，确保项目结构没问题，然后再根据用户需求逐步填充替换。这比"一口气生成完整应用"靠谱得多。

🎯 上下文窗口治理

分级消息窗口 + 多级压缩（micro/auto）+ 动态 System Prompt 追加。让 Agent 能在有限窗口内长期稳定运行，大幅降低幻觉和重复操作。
