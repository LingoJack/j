// part 01 · chatbot → agent

Chatbot 和 Agent 的区别：
谁来跨越现实与逻辑的鸿沟？

Chatbot

模型活在逻辑世界里，只输出文本。你需要自己把现实世界的信息搬过去——复制代码让模型看、把报错粘贴给它；模型说改哪行，你自己去改；模型说跑命令，你自己去跑。

你是现实与逻辑之间的桥梁。

Agent

模型通过工具直接触达现实世界——自己读文件、改代码、跑命令、搜网页。模型不再是孤岛，它可以自己去拿上下文、自己验证结果。

工具是现实与逻辑之间的桥梁。

先聊最根本的问题——Chatbot 和 Agent 到底差在哪？

我有一个理解方式：区别在于"谁来跨越现实与逻辑的鸿沟"。

Chatbot 活在逻辑世界里——它只产出文本。但软件工程是发生在现实世界的——文件在磁盘上、代码有编译结果、命令有输出。所以你用 Chatbot 的时候，你就是那座桥——你得自己把代码复制粘贴给模型看、把报错信息贴给它，模型说"改第 42 行"，你自己去改。

而 Agent 不一样。Agent 通过工具——读文件、改代码、跑命令——直接触达现实世界。工具取代了你，成了现实与逻辑之间的桥梁。模型不再需要你搬运信息，它可以自己去拿上下文、自己验证结果。

所以不是"Agent 加了个工具调用"这么简单——是桥梁从人变成了工具，是信息流转方式的根本改变。

// part 02 · function calling

Function Calling：
模型不执行，只输出参数。

核心思路：模型输出一个结构化的 tool_call（工具名 + JSON 参数），由调用方在受控环境中执行后回传结果。

①
推理与执行解耦

模型不会真的去删你的文件，它只是说"我想调用 DeleteTool(path=/tmp/x)"。

②
权限可拦截

执行方可以拒绝、弹确认框、记录审计日志——安全边界在执行侧。

③
多轮闭环

工具结果回传后，模型继续推理——形成"推理→行动→观察"的循环。

tool_call example
// LLM 输出：
{
  "tool_calls": [{
    "name": "Read",
    "arguments": "{\"path\":\"/src/main.rs\"}"
  }]
}

// 系统执行后回传：
{
  "role": "tool",
  "content": "fn main() { ... }"
}

那 Agent 是怎么获得行动能力的？答案就是 Function Calling——函数调用协议。

这个协议的核心思路特别巧妙：模型自己不执行任何操作。它只是输出一个结构化的 tool_call，说"我想调用 Read 工具，参数是 path 等于 /src/main.rs"。然后由系统侧的执行环境去真正执行这个操作，再把结果回传给模型。

这样设计有三个好处。第一，推理和执行解耦——模型不会真的去删你文件，它只是"想"删，你可以在执行前拦住它。第二，权限可拦截——你可以配置哪些工具需要人工确认、哪些可以自动放行。第三，多轮闭环——工具结果回传后模型继续推理，这就形成了一个循环。

这个循环就是我们接下来要讲的 ReAct 范式的基础。

// part 02 · react paradigm

react_loop
# ReAct 抽象循环
loop:
    observation ← env.feedback()
    thought, action ← LLM(history, observation)
    if action == DONE: break
    result ← execute(action)
    history.append(thought, action, result)

有了 Function Calling 之后，自然就会形成这样一个循环。但我想从另一个角度来理解 ReAct——它是让 AI 自己去找上下文的机制。

用 Chatbot 的时候，你得自己把信息搬给模型——复制代码、粘贴报错。但有了工具之后，Agent 可以自己去读文件、跑命令、搜网页，从现实世界获取观察，再基于真实信息继续推理。

所以 ReAct 的 Thought→Action→Observation 循环，本质上就是——Agent 不再靠人喂信息，而是自己去现实世界拿。工具是它伸向现实世界的手。

举个例子。你说"帮我把这个 bug 修了"，Agent 不是直接给你一段代码。它先想"我得先看看报错信息"，然后调用 Read 工具去看日志文件——拿到真实的报错行号，再想"这是空指针的问题"，再调用 Edit 工具改代码，再调用 Bash 跑测试看结果……每一步都建立在真实观察之上，而不是凭空猜测。

但 ReAct 有个问题——它只关注当前这一轮的决策，如果反复失败，可能会一遍一遍犯同样的错。这就引出了下一个范式。

// part 02 · reflexion paradigm

Reflexion：失败之后
写一段反思，下次不踩同一个坑。

ReAct 擅长"当下怎么决策"，但不擅长"上次为什么失败"。Reflexion 在一次尝试结束后，对失败原因进行语言化总结，注入下一轮上下文。

①
尝试

Agent 正常执行一次完整任务。

②
评估

检查结果是否满足约束。

③
反思

生成自然语言 reflection，记录错误与改进方向。

④
重试

把反思注入上下文，开始下一轮尝试。

reflexion_loop.py
# Reflexion 抽象循环
loop:
    candidate ← solve(task, memory)
    feedback ← evaluate(candidate)
    if feedback == PASS: break
    reflection ← generate_reflection(
        task, candidate, feedback
    )
    memory.append(reflection)

ReAct 有个明显的短板——它没有记忆。如果这一轮修 bug 失败了，下一轮它可能还是先去读同一个文件、犯同样的错。

Reflexion 就是来解决这个问题的。它的核心思想是：在每次尝试结束后，让 Agent 对失败原因做一段语言化的总结，然后把这个总结注入到下一轮的上下文里。这样下一轮开始的时候，模型就知道"上次为什么失败了"。

注意，这里的学习不是更新模型参数——模型权重不变。它是一种测试时（test-time）的语言反馈机制：把"上一次为什么失败、下一次应避免什么问题"显式写入记忆。

举个例子：Agent 第一次生成代码后，测试没通过，它反思说"我忘了处理空指针的情况，下次应该先做空值检查"。第二次再试的时候，这个反思就在上下文里了，所以它会先做空值检查。

// part 02 · 本文采用的混合范式

局部 ReAct + 全局 Reflexion。

局部：ReAct

各 Agent 围绕当前子任务进行推理→行动→观察的循环。读文件、改代码、跑测试——每一步都建立在真实信息上。

全局：Reflexion

阶段任务结束后，对需求满足度、代码质量、测试结果进行反思总结，沉淀到计划文档和记忆中。

为什么组合？

ReAct 保留灵活性（复杂交互中持续调整），Reflexion 吸收纠错能力（不在同一个坑里反复踩）。更符合真实软件工程的迭代特征。

所以我的系统用的是两者的组合。一句话概括就是——局部 ReAct，全局 Reflexion。

在局部执行层面，每个 Agent 都在做典型的 ReAct 循环——读文件、改代码、跑测试，每一步都根据环境反馈调整策略。

在全局优化层面，当一个阶段性任务结束后——比如后端 API 写完了——系统会对需求满足度、代码质量、测试结果做一次反思，把结论写到计划文档里。这样下一轮迭代的时候，Agent 就知道上一轮的问题在哪。

为什么不能只用一个？ReAct 灵活但没有经验积累，容易反复犯错；Reflexion 有纠错能力但不够灵活，不能处理"正在修代码突然发现另一个 bug"这种实时场景。所以组合起来最接近真实软件工程的迭代过程。

// part 03 · agent 的三道坎

从 Chatbot 衍生出来的 Agent，
面临三道坎。

1 · 上下文窗口

一个中型业务系统涉及数十个文件、数千行代码，远超模型有效上下文长度。"最大窗口"≠"有效上下文"，Lost in the Middle 现象让长上下文中部信息利用率骤降。

2 · 多 Agent 协同

单个 Agent 把所有任务压在一个对话线程里，会导致上下文污染、目标漂移。需要多角色分工，但协同又会引入通信、权限、一致性问题。

3 · 代码处理短板

业务系统中有大量模板代码（PO/DTO/DAO），让 LLM 逐字生成既慢又易错——字段名漂移、跨层不一致、Token 浪费。

讲完了 Agent 的基本原理，现在来讲为什么光有 Chatbot + Function Calling 还不够。

从 Chatbot 衍生出来的 Agent，在真正去写复杂业务软件的时候，会遇到三道坎。

第一道坎：上下文窗口。一个中型业务系统涉及几十个文件、几千行代码，远远超出模型的有效上下文长度。而且"最大窗口"不等于"有效上下文"——有研究指出，关键信息放在长上下文中部时，模型性能会明显下降，这就是所谓的 Lost in the Middle 现象。

第二道坎：多 Agent 协同。单个 Agent 把所有任务——需求分析、前端、后端、测试——都压在一个对话线程里，很容易上下文污染、目标漂移。需要多角色分工，但多 Agent 之间又有通信、权限、一致性的问题。

第三道坎：代码处理短板。业务系统中有大量模板代码——实体类、DAO、CRUD 接口——让 LLM 逐字生成既慢又容易字段名漂移、跨层不一致。

这三道坎就是我的课题要解决的核心问题。接下来我就围绕这三个问题，介绍 j-cli 的设计。

先整体看一下 j-cli 的架构。它是一个 Rust 写的命令行工具，整体采用四段式架构。

最外层是 CLI 入口，用 clap 解析命令，支持 28 个子命令——比如 j open 打开别名、j report 写日报、j chat 进入 AI 对话。如果你直接输入 j 不带参数，它会进入REPL 交互模式，有 Tab 补全和历史记录。

中间层是 Chat 核心，这是整个系统最核心的部分，也是我论文重点研究的对象。它内部包含消息存储、Agent 运行时、工具系统和能力扩展四个子模块。

最底层是持久化层，负责把会话、任务、技能和协作记录保存到磁盘，支持崩溃后恢复。

接下来我重点讲 Chat 核心里的几个关键设计。

// part 04 · 三通道消息架构

一条消息，三种形态。

Display 通道

面向终端界面。用户看到的干净气泡——去除 XML 标签，只显示有用的内容。

用户可读

面向 LLM 输入。保留 <Sender> 标签、工具完整结果——帮助模型区分不同角色发言。

模型可理解

面向持久化。保证崩溃后可恢复——只在"所有 tool_calls 都配齐 tool_result"的安全切点才写磁盘。

可重放

第一个关键设计是三通道消息架构。这是整个 Chat 核心的基础。

直觉上你可能觉得，消息不就是一条列表嘛，干嘛要分三个通道？其实当你引入多 Agent 之后，问题就来了——同一件事，UI、LLM、持久化三方需要的信息是不一样的。

比如 Teammate 的内部思考，用户不需要看到全部细节，但模型需要知道"谁说了什么"来区分角色。再比如工具的原始输出，可能有好几 KB，用户不需要全看，但模型在下一轮推理时可能需要引用。还有持久化，如果在流式生成中途崩溃，你不能把半截消息写进磁盘，否则重启后加载出一个不合法的会话。

所以我把消息拆成三个通道：Display 给用户看、Context 给模型读、Session 给磁盘存。同一个消息，三条不同的"投影"。

其中 Session 通道有个精巧的设计——安全切点。它只在"所有 tool_calls 都配齐了对应的 tool_result"的时候才写磁盘。这样即使崩溃，磁盘上的数据也一定是合法的。

// part 04 · 上下文窗口管理

有限窗口里，保留什么、丢弃什么？

优先级窗口 · 4 阶段选择

S1
时间保底

最近 K 个单元无条件保留。

S2
豁免保底

Skill、Task 等关键工具结果按时间倒序保留——不能被截断。

S3
比例配额

User:Assistant:Tool = 1:3:4，按时间倒序。

S4
溢出贪心

剩余预算按时间倒序贪心填充。

三级 Compact · 逐级压缩

级别触发器Token 开销
Micro每轮 Agent Loop0（替换旧工具结果为占位符）
AutoToken 触发阈值一次 LLM 调用（摘要整段历史）
Manual用户/Agent 主动一次 LLM 调用

有了三通道架构之后，下一个问题就是——上下文窗口怎么管理？

前面说过，"最大窗口"不等于"有效上下文"。一个中型业务系统很容易超出 100K tokens，所以必须有选择地保留信息。我的方案分两层——优先级窗口和多级 Compact。

优先级窗口是一个 4 阶段选择算法。第一阶段是时间保底——最近 K 个消息肯定保留，这是底线。第二阶段是豁免保底——Skill 加载结果、Task 状态这类"关键能力上下文"不能被截断。第三阶段是比例配额——用户消息、助手消息、工具结果按 1:3:4 分配预算。第四阶段是溢出贪心——还剩多少空间就再按时间倒序塞。

但光选还不够，会话太长时还得压缩。我设计了三级 Compact：Micro 是零成本的轻量替换，把旧的、大段的工具结果替换成占位符；Auto 是真正的摘要，用一次 LLM 调用把整段历史压成一段话；Manual 是用户或 Agent 主动触发的压缩。

这三层组合起来，就能在"完整保留上下文"和"控制成本"之间取得平衡。

// part 04 · skill 渐进式加载

能力不是一开始全塞进去，
用到再加载。

传统方式把所有能力写进 system prompt，导致两个问题：prompt 线性膨胀，LLM 每轮都要扫描全部细节。

①
启动时：只暴露元信息

System prompt 中只列出 skill 的 name + description，比如"jen：根据 SQL 生成 Go DAO"。

②
需要时：LoadSkill 全量注入

Agent 判断需要某 skill，调用 LoadSkill(name)，完整 SKILL.md 内容注入 Context 通道。

③
压缩后：自动恢复

Auto Compact 后 skill 内容可能丢失，系统记录 InvokedSkillsMap，在下一轮自动重新加载。

~/.jdata/agent/skills/
# skills/ 目录结构
sql-to-go-struct-and-dao/
├── SKILL.md        # 完整工作流说明
├── references/     # 参考文档
└── scripts/        # 辅助脚本

webapp-gen/
├── SKILL.md
├── references/
└── scripts/

下一个设计是Skill 渐进式加载。这个设计的出发点很简单——如果你把所有能力都写进 system prompt，两个问题：一是 prompt 膨胀，二是模型每轮都要扫描全部细节才能找到相关的。

我的方案是按需加载。启动时 system prompt 里只有每个 skill 的名字和一句话描述——比如"jen：根据 SQL 生成 Go DAO"。只有当 Agent 判断需要用到某个 skill 的时候，才通过 LoadSkill 工具把完整的 SKILL.md 注入上下文。

这个设计还有一个容易被忽略的细节——Auto Compact 后的恢复。因为 Auto Compact 可能会把 skill 的内容压缩掉，但 skill 又是"关键能力上下文"，不能丢。所以我维护了一个 InvokedSkillsMap，记录哪些 skill 已经加载过。Compact 之后，下一轮会自动重新加载这些 skill。

所以 Skill 机制不只是在做上下文优化——它也试图改善 Agent 对工作流的遵循能力。传统方式下，模型可能"知道"某个能力存在，但因为上下文太长而被淹没。显式触发 + 完整加载，让 Agent 在合适时机遵循对应步骤的概率更高。

// part 04 · 工具增强

工具不是"能用就行"，
得安全、可恢复、受约束。

Edit · 增强型编辑工具

预览-确认协议：replace_all 时先返回匹配预览 + confirm_token，必须携带 token 才执行替换——模型无法跳过预览。

文件级互斥锁：多 Agent 并发时，同一文件只能被一个 Agent 编辑，避免覆盖。

诊断性反馈：匹配失败时返回行号 + 上下文，引导模型修正，而非简单报错。

Plan · 先规划后实施

进入只读模式——Bash/Write/Edit 全部拦截，只放行 Read/Glob/Grep 等只读工具。规划不再是隐式思维，而是受工具约束、可审查的中间工件。

Hook · 工具调用前后拦截

在工具调用前/后插入自定义命令——比如每次写文件后自动跑 cargo fmt，或禁止在生产分支执行 git push。

Permission · 工具白/黑名单

基于 .jcli 文件的权限规则——Bash(prefix:*)、Write(path:dir/*)、WebFetch(domain:x)。Deny 优先于 Allow。

讲完上下文管理，接下来聊工具增强。这部分我想穿插一些个人的理解。

传统 code agent 的 Edit 工具就是"字符串匹配后直接替换"——在单 Agent 单轮修改时够用，但多 Agent 场景下就容易出问题。我做了三项增强。

第一，预览-确认协议。当 replace_all=true 做批量替换时，工具第一次调用只返回匹配预览和一个 confirm_token，不真正修改文件。第二次调用必须携带对应 token 才会执行。因为 token 跟文件内容绑定，模型无法跳过预览，也无法在文件变化后复用旧 token。

第二，文件级互斥锁。多个 Agent 同时改同一个文件怎么办？Edit 和 Write 在执行前会尝试获取文件锁，如果已被其他 Agent 占用就直接失败并返回占用方信息。

第三，Plan 模式。这是一个我特别想强调的设计——先规划后实施。进入 Plan 模式后，所有写工具都被拦截，Agent 只能用只读工具来了解代码库。规划不再是模型脑子里的事情，而是变成了一份可审查的文件。

还有 Hook 和 Permission——Hook 是在工具调用前后插入自定义逻辑，Permission 是控制工具能不能调。两者结合，让工具接口从"模型能否调用"扩展为"模型在什么条件下、以何种审计方式调用"。

// part 05 · 多 agent 协同

两种协同范式：
委派 vs 聊天室。

维度SubAgent（委派型）Teammate（聊天室型）
生命周期一次性，完成即销毁长期共存，与主 Agent 同寿
上下文独立 transcript，与主 Agent 隔离共享对话，全员可见
通信启动参数 + 单条结果消息SendMessage 广播 + @mention
工作目录独立 git worktree（可选）与主 Agent 同目录
适用场景并行子任务、不污染主对话角色化协作、跨 Agent 联调

进入第五部分——多 Agent 协同。这是我想重点讲的内容。

我的系统提供了两种互补的协同范式。SubAgent 是任务委派型——主 Agent 把一个子任务派给一个临时 Agent，它跑完就销毁，只回传一条结果消息。好处是上下文隔离，子任务的过程不会污染主对话。

Teammate 是聊天室型——多个角色 Agent 长期共存，共享对话流，可以互相发消息、@对方。适合需要频繁沟通、不断对齐中间状态的任务。

这两种范式不是互斥的。比如主 Agent 可以先用 SubAgent 并行收集信息，再创建 Teammate 做长期协作。

接下来我重点讲聊天室型，因为它背后的设计问题更多，也更有意思。

// part 05 · 聊天室型协同（重点）

Teammate 的核心问题：
谁说了什么，别人怎么知道？

SendMessage · 显式提交

Teammate 的普通文本输出不会自动广播——只有调用 SendMessage 的内容才进入共享协作空间。

①
显式提交

普通输出只是内部思考（Draft），SendMessage 才是 Commit。

②
来源标记

Context 通道保留 <Sender> 标签，帮助 LLM 区分不同角色。

③
全员可见

@Target 只是聚焦注意力，不改变广播属性——避免信息孤岛。

SendMessage Gate · 乐观锁

执行 SendMessage 前检查收件箱——如果有新消息到达，说明当前输出可能基于过期上下文。

✓
收件箱为空

正常广播。

✗
收件箱非空

暂缓发送，注入新消息，追加 system reminder 要求重新评估。

⚠
连续暂缓达上限

强制提交，避免死循环。

聊天室型协同最核心的问题是——谁说了什么，别人怎么知道？

直觉上可能觉得，每个 Agent 的输出都自动广播给其他人就好了。但这样会有一个大问题——"边想边说"的噪声扩散。一个 Agent 还没看到最新消息，就基于过期信息发了一段判断，其他 Agent 又基于这个过期判断继续推理，最终形成连锁误导。

所以我的设计是Draft/Commit 二阶段。Agent 的普通文本输出只是 Draft——用户能看到，但不会进入其他 Agent 的上下文。只有 Agent 主动调用 SendMessage，才算是 Commit——真正进入共享协作空间。

但这还不够。就算 Agent 决定发送消息，发送之前还有一个Gate——类似乐观锁。Gate 检查这个 Agent 的收件箱里有没有新消息。如果有，说明它刚才思考的时候错过了新信息，当前输出可能基于过期上下文——那就暂缓发送，先把新消息注入，让它重新评估。

这个设计本质上是一个轻量级二阶段提交——LLM 生成只是候选消息，通过 Gate 后才成为共享事实。它降低了并发对话中"旧上下文发言"的风险。

// part 05 · 唤醒与旁听

不是每条消息都要立即响应，
但最终都可见。

消息可见性

广播消息会进入所有 Teammate 的收件箱，在后续 drain 到消息历史中——保证信息最终可见。

执行唤醒

只有来自 Main 的消息或 @target 才设置唤醒标记——不被无关消息频繁打断。

工具调用摘要化

自己的工具结果保留完整内容；其他 Agent 的工具调用只保留"谁调了什么"的摘要——区分原始观察和协作结论。

统一治理

同一份 .jcli 权限规则、同一个工具注册表、同一套 Hook——主 Agent、SubAgent、Teammate 同一条安全边界。

最后补充两个聊天室型的关键设计——唤醒与旁听和工具调用摘要化。

如果每条广播都立即唤醒所有 Teammate，系统会出现频繁互相打扰、空转发言、上下文膨胀。所以我区分了"消息可见性"和"执行唤醒"——消息最终都对所有人可见，但只有相关消息才会唤醒你。来自 Main 的消息和 @你的消息才会让你开始新一轮推理。

另一个问题是工具调用。每个 Teammate 都会频繁调用 Read、Grep、Edit 这些工具。如果把每个工具的完整结果都广播，上下文会迅速膨胀。所以我的策略是摘要化可见——你自己的工具结果保留完整内容，其他 Agent 的工具调用只保留"谁调了什么工具"的摘要。需要显式共享的结论，要求 Agent 通过 SendMessage 主动提交。

这把"原始观察"和"协作结论"区分开了——工具输出是局部证据，SendMessage 是经过 Agent 筛选的协作事实。

还有一点：所有 Agent——主 Agent、SubAgent、Teammate——都受同一份 .jcli 权限规则和同一套 Hook 约束。统一治理面，避免角色越权。

// part 04 · 模板代码工程化生成

模板代码：不让 LLM 逐字猜，
让生成器确定性输出。

jen · SQL → Go DAO 层

MySQL 建表语句作为唯一事实源 → 解析字段、索引、类型 → 模板渲染生成 PO、DTO、VO、DAO。

核心收益：字段一致性↑、Token 消耗↓、可迭代性↑（改 schema 重新生成即可）。

webapp-gen · 全栈生成工作流

将"一句话需求→可运行全栈应用"组织为阶段化工作流：需求分析 → 前端设计 → 原型 → 后端设计 → 编码 → 容器化验收。

关键机制：文档化中间产物、前后端契约传导、三态容器化验证。

LLM 语义理解
→
准备参数 / Schema
→
确定性生成器输出
→
LLM 校验集成

最后讲一下模板代码生成，这是解决"代码处理短板"这道坎的方案。

业务系统中有大量"机械代码"——实体类、DAO、CRUD 接口——结构稳定、规则明确。让 LLM 逐字生成这些代码，既慢又容易字段名漂移。我的方案是LLM 负责语义理解和流程调度，确定性生成器负责输出。

具体实现了两个工具。jen 是基于 SQL 的 Go DAO 层生成器——你给它建表语句，它解析出字段、索引、类型映射，然后通过模板渲染生成 PO、DTO、VO、DAO 四层代码。好处是字段跨层一致、Token 消耗大幅降低、改了 schema 直接重新生成。

webapp-gen 是面向全栈生成的阶段化工作流——把"一句话需求到可运行全栈应用"组织成多个阶段，每个阶段有文档化的中间产物、有验收条件。关键机制是"前后端契约传导"——API 设计文档定义接口契约，前端和后端都从这个契约生成，避免字段名漂移。

// takeaways

带回去的三件事。

1 · Agent：工具取代人成为桥梁

Chatbot 时代你搬运信息，Agent 时代工具取代你成为现实与逻辑之间的桥梁——AI 自己去找上下文。

2 · 单 Agent 要跑得远，靠治理

三通道消息、优先级窗口 + 多级 Compact、Skill 按需加载、工具增强（Edit/Plan/Hook/Permission）。

3 · 多 Agent 要跑得稳，靠机制

Draft/Commit 二阶段提交、SendMessage Gate 乐观锁、唤醒旁听分离、统一治理面。

最后总结一下，希望大家带走三件事。

第一，Agent 的本质：工具取代人成为桥梁。Chatbot 时代，是你自己搬运信息——复制代码给模型看、把报错贴给它。Agent 时代，工具取代你成为现实与逻辑之间的桥梁——AI 可以自己去读文件、跑命令、搜网页，自己去找上下文。Function Calling 解耦了推理与执行，ReAct 让 AI 自己去找上下文，Reflexion 补上了经验积累。

第二，单 Agent 要跑得远，靠的是治理。三通道消息架构解决了信息对不同消费者的适配问题；优先级窗口 + 多级 Compact 在有限窗口内保留最有价值的信息；Skill 按需加载避免了 prompt 膨胀；Edit 的预览确认、Plan 的只读模式、Hook 的拦截能力、Permission 的权限控制——这些工具增强让 Agent 的行为更安全、更可控。

第三，多 Agent 要跑得稳，靠的是机制。Draft/Commit 二阶段提交避免了"边想边说"的噪声扩散；SendMessage Gate 用乐观锁降低了并发中"旧上下文发言"的风险；唤醒与旁听分离避免了频繁互相打断；统一治理面确保所有 Agent 在同一安全边界内运作。
