## Key Findings

### Architecture
- **Multi-threaded agent system**: Each teammate runs in its own OS thread
- **Message-based communication**: Via broadcast to pending_user_messages queues
- **Centralized management**: TeammateManager controls all instances
- **Thread-local isolation**: Agent identity and working directory per thread
- **Global file locks**: RAII-based coordination for file editing

### Status Tracking (Current)
- **Binary only**: is_running: Arc<AtomicBool> (true/false)
- **No intermediate states**: Can't distinguish working vs. idle vs. error vs. stuck
- **Display location**: System prompt only via "{{.teammates}}" placeholder
- **No UI panel**: Status not shown in dedicated interface

### Communication Mechanism
- **Broadcast model**: All teammates receive all messages
- **Queue-based**: pending_user_messages in each TeammateHandle
- **@mentions supported**: Optional targeting of specific teammates
- **TUI integration**: Messages displayed via shared_messages Arc<Mutex>

### Lifecycle
- **Creation**: User calls CreateTeammate tool → thread spawned with run_teammate_loop
- **Execution**: Main loop with LLM, tool execution, idle detection
- **Idle detection**: 120 polling rounds (~2 minutes) with no pending work
- **Termination**: Via cancel_token or idle timeout

### Critical Bug Found

**Session exit doesn't call manager.stop_all()**

Location: `src/command/chat/handler/tui_loop.rs` lines 604-645

Consequence:
- Teammates continue running after session exits
- Thread leaks accumulate in long-running server
- Memory and LLM API connections wasted
- Cleanup eventually happens via idle timeout (~2 minutes)

### Idle Detection Algorithm
```
120 consecutive rounds with:
- No new pending messages
- No tool calls generated by LLM
- Each round sleeps 1s checking for interrupts
≈ ~2 minutes total timeout
```

### Message Flow
```
SendMessage tool
    ↓
calls broadcast(message)
    ↓
injects to pending_user_messages of all teammates
    ↓
next loop iteration drains messages
    ↓
messages appear in LLM context
    ↓
teammate processes and responds
```

## Current Limitations

1. **No Rich Status States**
   - Can't track: working, waiting, error, stuck, completed-success, completed-failure
   
2. **No Error Tracking**
   - Tool execution errors don't affect status
   - No error history or error count
   
3. **No UI Panel**
   - Status only visible in system prompt text
   - No dedicated dashboard or indicators
   
4. **Idle Timeout is Approximate**
   - 120 polling rounds ≠ wall-clock time
   - Varies with LLM latency
   
5. **No Task Queuing**
   - Teammates must be told what to do
   - No job queue or priority system
   
6. **No Coordination Primitives**
   - Only broadcast messaging available
   - No request-response or synchronization patterns
   
7. **Session Exit Bug**
   - Missing cleanup call leaves orphaned threads
   - Resource leak in production environments

## Immediate Action Required

**Fix the session exit bug** - This is a simple but critical fix:

File: `src/command/chat/handler/tui_loop.rs`
Location: After line 605 (input_thread.shutdown())

Add:
```rust
// ★ 停止所有 teammates（关键修复：防止资源泄漏）
if let Ok(mut manager) = app.teammate_manager.lock() {
    write_info_log("ChatApp", "Stopping all teammates...");
    manager.stop_all();
    
    // 等待 teammates 完成（可选，带超时）
    for (name, handle) in &manager.teammates {
        match handle.wait_for_completion(std::time::Duration::from_secs(5)) {
            Ok(_) => write_info_log("ChatApp", &format!("Teammate '{}' stopped cleanly", name)),
            Err(_) => write_info_log("ChatApp", &format!("Teammate '{}' stop timeout", name)),
        }
    }
}
```
