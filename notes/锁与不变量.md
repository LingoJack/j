# 锁、不可重入、不变量 —— 一次完整讨论的笔记

> 起因：`/dump` 和 `/dump-processed` 卡死整个 TUI。根因是 `LoadTool::description()`
> 在已经持有 `deferred_tools` 锁的调用栈里再次 lock 同一把 `std::sync::Mutex`，
> 触发自死锁（self-deadlock）。
>
> 围绕这个问题展开了对锁、可重入、不变量的讨论。本文档是讨论的完整整理。

---

## 一、为什么 std 的 Mutex 不可重入

### 直接事实

`std::sync::Mutex` 不可重入。同一线程二次 `lock()` 会永久 block。

要重入只能用第三方：
- `parking_lot::ReentrantMutex` —— 但它给出的是 `&T`（不可变借用），写不了
- 自己用 `RefCell<T>` + thread_local 计数 —— 复杂、运行期 panic 风险

### 为什么这是主动设计选择

不可重入不是"功能缺失"，是**主动选择**。理由分多层。

---

## 二、锁的本质契约：保护"不变量"，不是保护"变量"

### 什么是不变量（invariant）

**不变量** = 数据结构在"对外可见"时必须满足的一致性条件。

简单说：**别人看到这个数据时，它必须是合理的、自洽的、能用的状态。**

### 例子

#### 例 1：双向链表

不变量：`node.next.prev == node` 且 `node.prev.next == node`。
即每个节点的 next 指向的节点必须反向指回来。

#### 例 2：银行账户系统

不变量：所有账户余额之和 = 总资产（守恒）。
任何时刻外人查账，总额必须对得上。

#### 例 3：缓存 + 索引

```rust
struct UserCache {
    by_id: HashMap<u64, User>,
    by_email: HashMap<String, u64>,  // email → id
}
```

不变量：`by_email` 里每个 id 在 `by_id` 里必须存在；反过来 `by_id` 里每个
user 的 email 都要在 `by_email` 里。两个 map 必须同步。

#### 例 4：本案的 `deferred_tools`

不变量比较弱但存在：`deferred_tools: Vec<String>` 在任何时刻都是当前所有
"延迟加载工具"的**完整且互斥**列表（没重复、没遗漏、不包含已加载的）。

---

## 三、不变量为什么会被"暂时打破"

很多操作做不到原子。要修改数据结构，往往得分几步。

### 双向链表删除节点 X

```
原状态:  A ↔ X ↔ B    (不变量成立)

步骤1:   A.next = B   (X.prev=A 还在指向 A，但 A 已经不指向 X 了 ← 不变量破了)
步骤2:   B.prev = A   (X.next=B 还在指向 B，但 B 已经不指向 X 了 ← 还没修好)
步骤3:   X.next = null
步骤4:   X.prev = null

最终:    A ↔ B   (不变量恢复)
```

中间步骤 1、2、3 这几个时间点，从外人视角看链表是**坏的**。

### 银行转账

```
原状态:  A=100, B=50    (总额=150)

步骤1:   A -= 30        (A=70, B=50, 总额=120 ← 守恒不变量破了！钱凭空消失)
步骤2:   B += 30        (A=70, B=80, 总额=150)

最终:    A=70, B=80    (总额=150，恢复)
```

步骤 1 后、步骤 2 前那个时间点，30 块钱"不见了"。

### 缓存 + 索引更新邮箱

```
原状态:  by_id={1: User(email="a")}, by_email={"a": 1}

步骤1:   by_id.get_mut(1).email = "b"   (by_id 更新, by_email 还指向旧 email)
步骤2:   by_email.remove("a")            (脱钩还在)
步骤3:   by_email.insert("b", 1)         (恢复)
```

步骤 1、2 这两个时间点，`by_email` 里查得到 `"a" → 1`，但
`by_id[1].email == "b"`，两个 map 在撒谎。

## 四、锁的真正职责

锁不是"让别人不能改这个变量"——那是 `&mut` 借用做的。

锁的真正职责是：**遮蔽中间态，让别人只能在不变量成立时观察到数据。**

```rust
fn transfer(&self, amount: u64) {
    let mut accounts = self.lock.lock();    // 进入临界区
    accounts[from] -= amount;                // 不变量破了（中间态）
    accounts[to] += amount;                  // 不变量恢复
}                                            // 出临界区，别人才能看
```

锁的契约：

> **进入临界区 = 不变量成立。临界区内可以暂时打破。
> 离开 = 必须恢复。外面的人只在"恢复后"看到数据。**

---

## 五、可重入怎么就破坏这个契约

关键例子：

```rust
fn transfer(&self, from, to, amount) {
    let mut accounts = self.lock.lock();
    accounts[from] -= amount;            // ← 不变量破了！总额少了 amount
    self.audit();                        // ← 此处调用一个内部方法
    accounts[to] += amount;              // ← 不变量恢复
}

fn audit(&self) {
    let accounts = self.lock.lock();     // ← 关键：这里又拿锁
    let total: u64 = accounts.iter().sum();
    log!("当前总额: {}", total);
}
```

### 不可重入锁的行为

`self.audit()` 里 `self.lock.lock()` → **死锁，程序卡住**。

死锁很烦，但它在替你喊：

> "嘿，你正打算让 audit 在临界区里观察 accounts，但此刻 accounts
> **不是合理状态**。要么把 audit 挪出临界区，要么先恢复不变量再 audit。"

死锁是**响亮的失败**——卡住、报错、栈打印——立刻就知道有问题。

### 可重入锁的行为

`self.audit()` 里 `self.lock.lock()` → 同线程，重入计数 +1，**直接通过**。

audit 拿到 accounts，遍历求和：

```
A=70, B=50  →  total=120  →  日志写 "当前总额: 120"
```

但**真实总额是 150**。30 块钱凭空消失被记成了"事实"，写进审计日志。

程序没卡。没报错。一切看起来正常运行。

**但日志里全是错的。**

如果 audit 不是写日志，是触发告警："总额异常，少了 30，疑似被盗刷"——
半夜被叫起来排查一个不存在的攻击。

如果 audit 是发 webhook 给监管系统——刚向监管上报了一笔虚假财务事件。

如果 audit 是触发风控规则自动冻结账户——冻结了一个无辜用户的钱。

**这才是"破坏不变量"的真实代价：错误数据看起来跟正确数据一模一样，
会被下游当成事实使用。**

## 六、为什么数据污染比死锁糟糕

| 维度 | 死锁（不可重入） | 数据污染（可重入） |
|---|---|---|
| 何时发现 | 立即（程序卡住） | 可能永远不发现，或下游崩了才回溯 |
| 能否复现 | 100% 复现 | 时序相关，难复现 |
| 错误传播 | 不传播（直接停） | 沿调用链、写进日志/数据库/外部系统 |
| 排查难度 | 看栈即可 | 要追整条数据流，可能跨进程跨服务 |
| 影响 | 这一次操作失败 | 历史数据污染，难回滚 |

并发编程里的格言：

> **"Fail loudly, fail early."（响亮地失败，尽早失败。）**

死锁是响亮的、立刻的失败。数据污染是沉默的、延迟的失败。
两害相权，取响亮。

## 七、可重入锁还有哪些代价

### 1. 锁是"对象级"还是"调用栈级"模糊

不可重入锁：lock 是**对象层面**的——某时刻某把锁要么有人持要么没人持，
所有权清晰。

可重入锁：lock 是**调用栈层面**的——同线程的不同栈帧都"持有"这把锁，
但谁负责维护不变量？外层？内层？两层都是？没法说清。

trait/虚函数/回调场景尤其糟糕。本案的 `LoadTool::description()` 就是这种：
外层 `build_tools_summary_non_deferred` 持着锁、调到了 trait 方法、trait
方法又拿同一把锁——**外层根本不知道内层会拿锁，内层根本不知道自己被外层
包裹了**。这种情况"重入锁让它能跑"是用方便掩盖了一个真正的设计错误：
trait 契约和锁契约对不齐。

### 2. 公平性 / 移交语义崩溃

不可重入锁可以做到 fair queuing——按等待顺序唤醒。
可重入锁不能，因为同线程要优先（否则它自己会饿死自己）。这意味着：

- 锁的等待队列变得不可预测
- 跨线程"接力交接"困难（可重入锁不能 unlock 后让别的线程接管）
- `Condvar::wait` 之类协作原语必须知道当前重入计数才能正确释放锁

`std::sync::Condvar` 假设 `Mutex` 不可重入；换成可重入锁配合 `Condvar`
就得加额外协议。

### 3. 性能也变差

可重入锁要存：
- 当前持有者的线程 ID
- 重入计数器

每次 lock/unlock 都要比较线程 ID + 增减计数。即使无竞争路径上也有开销。

不可重入锁的 fast path 可以是单条 CAS。

### 4. Rust 的额外约束：借用规则

Rust 标准库选不可重入有更深一层原因：**借用规则**。

`Mutex<T>::lock()` 返回 `MutexGuard<T>`，它 deref 成 `&mut T`。可重入 lock
意味着同线程能拿到**两个 `&mut T`**——直接违反 Rust 的"同时只能有一个
可变借用"基本规则。

所以 `parking_lot::ReentrantMutex<T>` 只能给 `&T`（不可变借用）。
要写就得套 `RefCell`：

```rust
ReentrantMutex<RefCell<T>>
```

借用检查从编译期挪到运行期，等于把"该不该重入"这个本来由编译器保护的
问题，变成"运行时 panic"风险。这正是 Rust 想避免的。

## 八、业界经验

- Java 的 `synchronized` / `ReentrantLock` 是可重入的，被认为是早期设计
  失误之一。Doug Lea（`java.util.concurrent` 作者）后来反思过：可重入是
  为了适配 `synchronized` 历史包袱，并非好设计。

- POSIX `pthread_mutex` 默认不可重入，重入是 opt-in 的
  `PTHREAD_MUTEX_RECURSIVE`，文档明确说"避免使用，除非移植旧代码"。

- C++ `std::mutex` 不可重入；`std::recursive_mutex` 存在但被 Herb Sutter
  等人公开建议"几乎从不该用"。

> "If you find yourself wanting a recursive mutex, you have a design problem."
> —— 这句话在并发编程社区是共识。

## 九、不可重入 vs 可重入：总览

| 维度 | 不可重入 | 可重入 |
|---|---|---|
| 不变量保护 | 强（强制你在出临界区前恢复） | 弱（中间态可能被看见） |
| 死锁 | 响亮失败，立刻暴露问题 | 沉默通过，掩盖结构问题 |
| 调用栈 → 锁所有权 | 清晰（对象级） | 模糊（栈级） |
| 配合 Condvar / fair queue | 自然 | 需额外协议 |
| 性能 | fast path 极简 | 多一次 TID 比较 + 计数 |
| Rust 借用规则 | 直接给 `&mut T` | 只能 `&T`，要写得套 `RefCell` |

## 十、"想要可重入锁"通常对应的结构问题

这是经验法则，几乎是并发编程里的铁律。展开讲。

### 1. 临界区里调了不该调的东西

最典型。临界区的设计原则是：**短、纯、不出锁**。

"出锁"指的是调用 trait 方法、虚函数、用户回调、跨模块函数——这些你不知
道它们内部会做什么的调用。

```rust
let guard = self.state.lock();
self.notify_observers();   // ← 出锁了。observer 是用户注册的，鬼知道它干什么
```

如果 observer 又回头调到需要这把锁的方法，不可重入锁会卡死，告诉你：
**临界区不该调出去**。换成可重入锁能跑，但你把临界区的边界让给了外人，
不变量是否被破坏不可控。

**正确响应**：把 `notify_observers()` 挪到 `drop(guard)` 之后；或者只在
锁内复制需要的数据，出锁后再通知。

### 2. 一把锁保护了太多东西

锁的粒度过粗，导致一个操作里多个子步骤都要"摸"同一把锁。

```rust
let guard = self.everything.lock();
self.do_a(&guard);          // 内部又想 lock everything
self.do_b(&guard);          // 同上
```

想要重入，是因为子步骤被建模成"独立的有锁方法"，调用方又想把它们组合起来。

**正确响应**：拆锁。或者把"需要锁的部分"和"不需要锁的部分"分开，子方法
接收 `&mut Inner`（已经在锁内的数据）而不是 `&self`（还要自己拿锁）。

```rust
// 反模式
fn do_a(&self) { let g = self.lock.lock(); ...g... }
fn do_b(&self) { let g = self.lock.lock(); ...g... }
fn combined(&self) { self.do_a(); self.do_b(); }  // 锁两次，且非原子

// 正模式
fn do_a_inner(inner: &mut Inner) { ... }
fn do_b_inner(inner: &mut Inner) { ... }
fn combined(&self) {
    let mut g = self.lock.lock();
    do_a_inner(&mut g);
    do_b_inner(&mut g);
}
```

### 3. 接口契约和锁契约对不齐（**本案就是这种**）

`Tool` trait 的 `description(&self) -> Cow<str>` 这个方法，从签名和命名
上是"廉价的、纯查询的元数据"。任何一个实现者读到这签名都不会预期它内部
要拿运行时锁。

但 `LoadTool` 偏偏让 `description()` 锁了运行时状态。于是：

- `build_tools_summary_non_deferred` 的作者：以为遍历 `description()`
  是纯查询，把外层 lock 透传进来
- `LoadTool` 的作者：觉得 `description()` 拿一下 lock 没什么大不了

两边的契约假设不一致，运行时撞死锁。

可重入锁能让它"跑通"——但**没解决契约不一致**。下个加 tool 的人还会踩
同样的坑。

**正确响应**：让 `description()` 名副其实地静态。要"动态"信息（当前
deferred 名单），换个机制传。

### 4. 把"协议"塞进了"机制"

可重入锁的另一种典型动机是：

> 我有些函数预期被外部调用（拿锁），有些函数预期被内部调用（已经在锁里）。
> 我懒得分两套，一套搞定。

这是把**协议层面的区分**（这个函数是给谁用的？）塞进了**锁机制**
（让锁来包容两种用法）。代价是任何一处调用都看不出"现在是不是已经在
锁里了"，可读性下降，bug 排查困难。

**正确响应**：用类型系统标记。给"已经在锁里"的版本接 `&mut Inner`，
给"没在锁里"的版本接 `&self`。编译器一眼看出区别。

### 5. 递归数据结构 + 整树锁

少数情况下你真的需要遍历一棵树，每个节点都有锁，递归过程中可能回到祖先
节点。这种场景看起来像"必须可重入"——但其实更深层问题是：

- 锁粒度选错了（应该 per-node 还是整棵树一把锁？）
- 遍历算法选错了（递归 vs 迭代 + 显式栈）
- 数据结构选错了（也许该用 immutable + COW，根本不需要锁）

可重入锁是给你一条"绕过去想清楚"的路，但绕过去的代价是上面 1-4 节的所
有问题。

## 十一、什么时候可重入是合理的

少数场合可重入锁是合理的：

- 跨语言绑定（FFI 必须保证回调安全）
- 历史 API 兼容（Java `synchronized` 这种）
- 真递归的数据结构（编译器 AST、UI 层级）且 per-node 锁不可行

但这些场合的共同特点是：**你被外部约束逼着接受次优方案**，而不是"我设
计新东西时主动选可重入"。

## 十二、自检清单

每次心里冒出"要是这把锁可重入就好了"，停下来问：

1. **临界区里我调了什么 trait/虚/回调?** → 把它挪出去。
2. **同一把锁的多个方法被组合调用?** → 拆 inner / outer，inner 接
   `&mut Guard`。
3. **某个方法在"持锁"和"不持锁"两种上下文里都被调用?** → 拆成两个方法，
   类型签名区分。
4. **数据结构本身递归?** → 重新想锁粒度。

四个问题里只要有一个"是"，就别换可重入锁，去改结构。如果四个都"否"——
那大概率是真的需要可重入，可以用，但请在代码里注释清楚为什么。

## 十三、回到本案

`/dump` 卡死的根因：`LoadTool::description()` 在已持有 `deferred_tools`
锁的调用栈里再次 lock，触发 `std::sync::Mutex` 的自死锁。

调用链：

1. `dump_current_request` → `app.build_current_system_prompt()`
   ([system_prompt.rs:118](src/command/chat/app/system_prompt.rs#L118))
2. 锁住 `self.deferred_tools` 拿到 `guard`
3. 把 `&guard` 传给 `build_tools_summary_non_deferred`
   ([definition.rs:342](src/command/chat/tools/definition.rs#L342))
4. 该函数遍历 tools 调 `t.description()`，遍历到 `LoadTool` 时
5. `LoadTool::description()` 再次对**同一个** `self.deferred_tools`
   `.lock()`（[load_tool.rs:42](src/command/chat/tools/load_tool.rs#L42)）
   → 永久 block

对应的结构问题（第十节 3 号）：trait 契约（`description` 是廉价静态查询）
和实现（`LoadTool` 让 description 拿运行时锁）**对不齐**。

如果当时换成 `parking_lot::ReentrantMutex`：
- 死锁消失 ✅
- 但 `description()` 依然在运行时拿锁（性能问题）
- 但 trait 契约依然被违反（下一个加 tool 的人还会踩坑）
- 但 `LoadTool::execute()` 里要写 `deferred.remove(i)`，需要 `&mut`，
  `ReentrantMutex` 给不了，得套 `RefCell` → 借用检查从编译期挪到运行时
- **一次结构性问题被压成了三个潜伏问题**

正确响应是改结构：让 `LoadTool::description()` 不再依赖运行时状态，
要么完全静态，要么由调用方从外部注入 deferred 列表。

---

## 一句话总结

**锁保护的不是"变量不被改"，是"中间态不被看"。可重入意味着"中间态可以
被同线程的下一层栈帧看到"——这恰恰就是锁本来要防的事。**

"为什么不可重入"和"为什么不变量会被影响"是同一个答案的两面：
锁的存在意义就是遮蔽中间态，而重入是给中间态开了个后门。

死锁是响亮的失败。错误数据是沉默的失败。软件工程更怕沉默的失败。
